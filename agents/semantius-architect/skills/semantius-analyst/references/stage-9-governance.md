# Stage 9 + 9.5: FK validation and RACI / persona reconciliation

*Reference for `semantius-analyst` (Stages 9 and 9.5).*

## Stage 9: Cross-tier FK reconciliation (validation-only)

The blueprint carries authoritative `write tier` per §3 row and authoritative `fk_format` per §5.1 / §5.2 row, so Stage 9 is a **validation-only** sweep:

1. **Confirm every entity's `write tier`** from §3 lines up with §8.1 permissions: a `:manage` row has a `<slug>:manage` permission; a `:admin` row has a `<slug>:admin` permission; a narrow tier has its `narrow` row; a `:read` row is reference-only (no write tier). At every level but `custom`, also confirm each entity's own rows against "Which rows an entity gets" in `semantic-spec-template.md` (§8.1): its `entity-read` and `entity-write` rows, and its §9.1 bundle rows. Mismatch → 🔴 blocker (the architect should have caught it).
2. **FK shapes** are checked and fixed by the Stage 8 FK scope fix (it needs the Stage 10 rules).
3. (Covered by rule 2.)
4. **Validate `label_parent` is internally consistent.** For every entity carrying a `**Label parent:**` line (derived in Stage 4): the named field must be a real `reference`/`parent` FK declared on that entity in §3, and must NOT target a `junction` entity; and the line must NOT appear on a `junction` entity. A violation is a 🔴 blocker (a failure here means the derived spine name and the field list disagree). The `label_parent` graph across entities must be acyclic; a suspected cycle is a 🔴 blocker.
5. **Validate key types.** For every entity carrying a `**Key type:**` line (carried from the blueprint's §3 `**Key types:**` sub-block): the value is one of `bigint` / `text` / `uuid` / `typeid` / `is_a` / `has_a` (never `computed`, which the platform refuses for a new entity; `auto_increment` is written by omitting the line); `typeid` and `is_a` REQUIRE a `**Key prefix:**` line and any other type forbids one; the prefix matches `^[a-z](?:[a-z_]{0,61}[a-z])?$`; no two entities of the spec share a prefix; and a prefix on an entity this spec provisions is not already used by another live entity (the Stage 2c index carries `id_prefix`). Each violation is a 🔴 blocker; a live prefix collision is resolved by picking a different prefix (tell the user plainly: the short prefix shown at the start of every record id is already used by `<other Plural Label>`).
   **Family validity** (platform facts: `../../use-semantius/references/entity-families.md`), each a 🔴 blocker:
   - every `is_a` / `has_a` entity has a `**Based on:**` naming an entity of the spec (or one reused live), never a built-in, with no cycle;
   - the base's key type fits: `typeid` for `has_a`; `typeid` or `is_a` for `is_a`. A base provisioned by this spec is checked in the file; a reused base against the Stage 2c index (live, managed, right key type);
   - no based entity carries `**Label column:**`, `**Label parent:**` or `**Order column:**`, or repeats a field of any level above it;
   - `<table_name>_ext` is free live for every based entity this spec creates, and no `table_name` ends in `_ext`;
   - **no cascade on an `is_a` entity's FKs**: every §4 row whose `FK table` is an `is_a` entity is `restrict` or `clear`;
   - **writers of a based entity also write its base.** Same module: the same bundle includes the based entity's write permission and its base's (the same write tier). Base in another module: a cross-module §9.1 Permission hierarchy row `` | `<slug>:<tier>` | `<base edit_permission>` | ✨ to create | `` (shape in `stage-3-shared-base.md` → Permissions).
   The file-level part is enforced by `consistency-check.ts`.

This stage does not rewrite FK shapes; the Stage 8 FK scope fix does.

## Stage 9.5: §9 RACI + persona reconciliation (dual-path)

The blueprint's §9 governance section is the authoritative carrier of baseline roles + permission hierarchy + RACI realization + functional ownership. This stage reconciles each row against the live catalog and emits drift annotations.

**Two paths, chosen by RACI mode.** The platform's live-RACI engine (catalog tables `processes` / `raci_assignments` / `process_gates` / `raci_events`; operators `is_raci_actor` / `has_consultation`) lets this stage run one of two ways per module:
- **`documentation` mode (default):** compile the RACI matrix into RBAC grants (Step 3 documentation path). The process axis, the R/A/C/I letters, and agent actors are not stored live.
- **`living` mode:** plan the live RACI rows (`processes`, `raci_assignments`, `process_gates`) and the enforcement rules (`is_raci_actor` / `has_consultation`) the deployer authors — **in addition to** the baseline tier grants that table access still requires. The matrix becomes queryable and enforced live.

**Step 0 derives the mode** (below; auto-derived from instance state, NOT a user question). Steps 1–2 (RBAC scaffolding) and 4–5 run in both modes; Step 3 branches.

> **Access-level short-circuit.** The RACI parts of this stage (Step 0, Step 3, the RACI realization, the Processes catalog, `raci_mode`, and `persona`) run only under `access_scope: raci`. Under every other access level:
> - **`advanced` / `gated`:** Steps 1–2 emit the viewer + manager + admin roles (role slugs normalized `-`→`_` per Step 1) and the hierarchy; Steps 4–5 (functional ownership, handoffs) run as documented; the Processes catalog is emitted as `_(none: access level <value>)_`; no RACI mode, RACI realization or RACI plan lines; no `persona` frontmatter. Under `gated` the hierarchy also carries one `<slug>:admin` → gate row for every `workflow-gate (lifecycle)` gate, high-risk gates too: the admin role takes every gated step.
> - **`basic`:** emit only the viewer + manager roles, the single `<slug>:manage → <slug>:read` hierarchy row and the per-entity bundle rows (every write under `<slug>:manage`), and skip the Processes catalog and §9.2 functional ownership (emit each as `_(none: basic access)_`). No RACI mode, RACI realization or RACI plan lines; no `persona` frontmatter.
> - **`custom`:** emit no roles and no hierarchy rows (the module's permissions were set up by hand), and emit the Processes catalog and §9.2 functional ownership as `_(none: permissions set up by hand)_`. No RACI mode, RACI realization or RACI plan lines; no `persona` frontmatter.
> The RACI lines are absent, not placeholdered: `consistency-check.ts` reads a `**RACI realization:**` line as a RACI matrix and then requires `raci_mode`.
> (See "What each access level authors" in SKILL.md.)

**Dropped entities (runs first, at every access level).** An entity whose `**Reconciliation:**` starts with `dropped` is not deployed, so what depends only on it leaves the spec before the steps below. Apply each item where the access level authors that row:

1. **§8.1 gates.** Remove a `workflow-gate (lifecycle)` row when every state it gates is on a dropped entity, or, for a `create` gate, when its entity is dropped. A gate that also covers a kept entity stays, and its `description` names only the kept states.
2. **§8.1 entity rows, overrides and §8.2 rules.** Remove the `entity-read`, `entity-write` and `override` rows and every §8.2 rule on a dropped entity. Step 3 skips an Additional Requirements override on a dropped entity.
3. **§9.1 hierarchy.** Remove every row that includes a permission removed above.
4. **§9.1 RACI rows and processes.** Take each removed gate out of its `grant gates [...]` list, and each event on a dropped entity out of its `trigger_events [...]` list. A row whose gate list empties reads `the gated entities' write tier`, and an `informed` row with no event left goes. Those two lists are the only place the blueprint says which entity a process depends on, so remove a process from the Processes catalog, with all its RACI rows, when it had an entry in either list and has none left. A process that never had one stays.
5. **Frontmatter `persona`.** Remove an actor whose last RACI row went, because the list equals the RACI `actor` column.
6. **§6 relationships and outbound handoffs.** Remove a §6 relationship row with a dropped entity at either end, and an outbound handoff whose `payload` is a dropped entity. An inbound row stays, because its payload belongs to the source module.

Step 3 works only on what remains, so the living-mode `_raci_assignments_`, `_process_gates_` and `_enforcement rules_` never name a dropped entity. The pre-save `consistency-check.ts` run fails a spec whose §6, §8 or §9 still depends on one.

**Step 0 — RACI mode (auto-derived from instance state; NOT a user question).** Step 0 runs only under `access_scope: raci`. Whether this module is `living` or `documentation` is decided by the catalog, never by a prompt. The only meaningful signal is whether the instance already runs RACI, and that is a fact about live state, not a user preference. Derive it silently:

- **Honor an explicit signal first, if present:** an architect `raci_mode` frontmatter hint, or the triggering request explicitly asking for live / enforced / audited process rules ("enforce RACI", "with live approvals and an audit trail"). Either one pins the mode.
- **Otherwise compute from live state:** is any module already using RACI? (`GET /processes?limit=1` non-empty, or any `modules.settings.raci_mode = living`). **`living` when ≥1 module already does; `documentation` when none do.** A greenfield instance with no RACI elsewhere derives `documentation` (do not impose live-process overhead on a setup that is not using it); an ATS added to an org already running RACI derives `living`.
- If the live instance lacks the RACI engine entirely (no `processes` entity registered), force `documentation`.
- **Do NOT fire an `AskUserQuestion` for this.** There is no Enable-RACI widget. The access level was decided by the architect; selecting documentation vs living is this derivation's job, not a prompt.
- **Record the derived `raci_mode` and its provenance:**
  - **Frontmatter:** `raci_mode: <living|documentation>` and `raci_mode_source: <computed-default|non-interactive>` (`computed-default` for the value derived on an interactive run; `non-interactive` for headless runs). This gate never produces `user-answer` (there is no widget to answer).
  - **§9 header line:** `**RACI mode:** \`<living|documentation>\`` (must match the frontmatter `raci_mode`).
  - **Customizations file:** persist `.raci.<module_slug>.mode` and `.raci.<module_slug>.source` to `$CUSTOMIZATIONS_FILE` via `yq`, so the derived choice is reused (and hand-editable) on re-deploys.
  - **Mechanical backstop:** the Stage 11 pre-save gate (resident in SKILL.md under "Verification gates"; the `consistency-check.ts` run) still rejects any spec that carries a RACI matrix but is missing `raci_mode` / `raci_mode_source`, or whose §9 line disagrees with frontmatter.

**Step 1 — Baseline-role drift.** Walk §9.1 baseline roles. **Normalize every role slug to the platform's `roles.slug` rule (`^[a-z0-9_]+$`) before emitting it to the spec: replace each `-` with `_`.** `module_slug` and the permission prefix derived from it may contain hyphens, but `roles.slug` may not, so the blueprint's `<system_slug>_<tier>` form (e.g. `ben-admin_viewer`) becomes `ben_admin_viewer` in the spec. This is the ONE place the normalization lives: the spec's §9.1 `role` column then carries the resolved, deploy-ready slug, and the deployer creates it verbatim without ever re-deriving `<slug>_<tier>`. Apply the identical `-`→`_` rule to every role-slug reference in the §9.1 RACI-assignment `role (slug)` column and the §9.2 functional-ownership rows, so all three sections resolve to the same role. Then, for each normalized row `<role_slug> | <slug>:read` etc., look up the role by `slug`. If missing, mark `✨ persona role to be created` for the deployer's Stage 4a-scaffold to mint. If present with mismatched `module_id` (a prior install attached it to a different module), mark as 🟡 drift. **Cell vocabulary:** the §9.1 baseline-roles `reconciliation` cell carries exactly one of the template's literal values `✨ to create` (missing) / `♻ exists` (present, same module) / `🟡 drift on module_id` (present, other module); the descriptive marks in this file are plan narration, not cell text.

> **Baseline-roles table columns `origin` and `catalog role code` (OPTIONAL, derived, display-only).** The §9.1 baseline-roles header is `| role | baseline grant | origin | catalog role code | reconciliation |` (the two columns inserted before the final `reconciliation`). They carry live `roles.origin` / `roles.catalog_role_code`, which the deployer RE-DERIVES from module type / slug, so round-trip through them is a functional no-op. The analyst leaves them BLANK (or omits the two cells) in a hand-authored spec; `semantius-optimizer` fills them from live state in a reverse-engineered one. They are NOT drift inputs — Step 1 above reconciles only `role` + `baseline grant`, never `origin` / `catalog role code`. A 3-column form (no `origin` / `catalog role code`) also parses (the modeler reads the table by header name).

**Step 2 — Permission-hierarchy drift.** Walk §9.1 hierarchy rows. For each `<perm_A> includes <perm_B>` relationship:
- Look up `permission_hierarchy` by its two permission names (`including_permission_name=eq.<perm_A>&included_permission_name=eq.<perm_B>`; the row `id` is the text `"<perm_A>.<perm_B>"`). Missing → the row's `reconciliation` cell carries `✨ to create` (narrated as `✨ hierarchy relationship to be added`; the deployer's Stage 2a-scaffold step 3 mints it); present → `♻ exists`. Mismatched `origin` is 🟡 drift.
- Validate both perms appear in §8.1. Missing → 🔴 blocker (architect-side bug; the §9 hierarchy can't reference a perm that doesn't exist).
- At every level but `custom` the relationships include the bundle rows: `<slug>:read` → each `entity-read` code; `<slug>:manage`, `<slug>:admin` or the narrow tier → each `entity-write` code, by the entity's write tier (always `<slug>:manage` under `basic`); and each `entity-write` code → its entity's `entity-read` code. A missing one is 🔴.
- Under `gated` and `raci` the relationships include one `<slug>:admin` → gate relationship per `workflow-gate (lifecycle)` gate, naming the gate's literal §8.1 code, except, under `raci`, a high-risk gate (§8.1 `high risk?` ✓), which has none. This is the admin override: when the Accountable person is absent or a record is stuck, an admin can take the step.

**Step 3 — Actor resolution + per-mode realization.** Walk §9.1 RACI rows. First resolve every actor to a `role_id`:
- **Persona** (`kind = persona`): compute the slug (lowercased, underscored, hyphens → underscores): `RECRUITING-RECRUITER` → `recruiting_recruiter`. Look up the role by `slug`; missing → mark `✨ persona role to be created` (deployer's Stage 4k mints it).
- **Skill** (`kind = skill`): resolve to a **role held by an agent user** (`users.is_agent = true`) — the agent-native parallel to a persona. Compute the slug the same way; missing → mark `✨ agent-held role to be created` **and** `✨ agent user to be provisioned` (deployer's Stage 4k). No separate `personas` / `skills` record — the matrix is `role_id`-only.

**Persona overrides (both RACI modes).** When the blueprint's `## Additional Requirements Specification` says a persona holds a `view_all_<plural>` or `manage_all_<plural>` override, append ` + grant overrides [<code>]` to the `realization` of that persona's first `responsible` or `accountable` row left after "Dropped entities" above, or of its first row of any kind when it has neither, using the code exactly as its §8.1 `override` row writes it. Mark `✨ persona grant to be added` for Stage 4k. A persona with no row left holds no override: say so in §7.2.

Then realize, **by RACI mode:**

**_`documentation` mode (default)_** — compile to grants:
- For each `raci = responsible | accountable` row → compute the granted permission codes. Both get the unit's bundles for the gated entities' write tier (`<slug>:manage` and `<slug>:read`). On an `:admin`-tier gated entity they get that entity's `write_<entity>` code instead of `<slug>:admin`, because `<slug>:admin` would also hand them every gate that is not high risk. Only the accountable row gets gates, and a responsible row is granted no gate. Each gate in the accountable row's `grant gates [...]` list (the accountable row of each process lists that process's gates: the RACI rule) is granted as §8.1 writes it, whichever module its prefix names. Mark each `✨ persona grant to be added` for Stage 4k.
- For each `raci = consulted` row → mark `✨ advisory read grant to be added`.
- For each `raci = informed` row → mark `✨ notification side-effect to be wired` (deployer's Stage 4m if the platform exposes triggers; otherwise a 🟡 informational row).

**_`living` mode_** — plan the live RACI rows + enforcement. **The baseline tier grant is still emitted** (RLS is permission-based, so an actor still needs the write tier to touch the table; it takes the same bundles and the same `write_<entity>` exception as `documentation` mode). **No gate is granted to the accountable role:** the A-gate rule below resolves it live from `raci_assignments`. The admin role holds every gate except a high-risk one through the §9.1 hierarchy (Step 2), and the same rule lets it take the step. On top of that:
- **`processes`** — one row per Processes-catalog entry: `{process_key, name, description, ordering, module_id = installing unit}`. **Carry `name` and `description` through VERBATIM** — copy them byte-for-byte from the blueprint Processes catalog. They are authoritative reference content (often PCF-sourced); do NOT paraphrase, summarize, reword, shorten, fix grammar, or "clean up" the description. Rewriting it breaks traceability to the source taxonomy. Set `ordering` from catalog order. Reconcile against live `GET /processes?process_key=eq.`: reuse on match, else mark `✨ process to be created`.
- **`raci_assignments`** — one row per RACI cell: `{process_id, role_id, raci, consult_mode}`. Mark `✨ raci assignment to be added`. **Verify exactly one `accountable` per process** (the RACI rule) (the platform enforces a partial unique index; the analyst pre-checks for a clean error).
- **`process_gates`** — bind `(entity, to_state, gate_kind)` to the process. **Never on an `is_a` / `has_a` entity** (the platform refuses it, `90249`; `consistency-check.ts` fails the save): gate the transition on an entity that is not based on another, or record the gate in documentation mode only. **Emit `state_column` as `workflow_state`** — the fixed lifecycle state field name (every entity with a §7 lifecycle stores its state there). Never emit any other column name; the deployer rejects a `state_column` that isn't `workflow_state`. Set `emits_events = true` when the process has any `consulted (notify)` or `informed` actor. Mark `✨ process gate to be added`.
  - **A `create` gate** (a §8.2 rule with source flag `create`) gets its own row: `gate_kind` `create`, `to_state` the entity's `initial?` §7 state, so the create A-gate below resolves its Accountable.
- **Enforcement rules** (the deployer authors these as `validation_rule` / `select_rule`, same mechanism as Stage 10). The §9.1 `_enforcement rules_` table is the one home of the living-mode gate rules (transition A-gates, create A-gates, C-blocks): none of them is also written into the entity's §3 `validation_rules`. Each row carries only its JsonLogic; the modeler derives the rule's `name`, `code` and `message` (modeler Stage 4k).
  - **A (accountable), the A-gate:** the gate rule on the transition into `<to_state>`, with the Accountable check and the gate's own permission in one `or`: `{"if": [{"and": [{"value_changed": "workflow_state"}, {"==": [{"var": "workflow_state"}, "<to_state>"]}]}, {"or": [{"is_raci_actor": ["<entity>", "<to_state>", "accountable"]}, {"has_permission": "<gate>"}]}, true]}`, where `<gate>` is the code as §8.1 writes it. This is the living realization of the gate rule that `documentation` mode writes as a §3 `validation_rules` entry with `has_permission` alone (Stage 10, "Gate rules"); in `living` mode it is written only here. The deployed rule carries its own `code` and `message` (e.g. "Only the hiring manager or an admin can approve an offer"; on a high-risk gate, "Only the hiring manager can approve an offer"). `has_permission` never throws, so the rule keeps its own `code` and `message` and the `or` works in either branch order.
  - **A for a `create` gate, the create A-gate:** the insert rule with the same `or`, where `<initial state>` is the entity's `initial?` §7 state (the `to_state` of its `create` `process_gates` row): `{"if": [{"==": [{"var": "$old"}, null]}, {"or": [{"is_raci_actor": ["<entity>", "<initial state>", "accountable"]}, {"has_permission": "<gate>"}]}, true]}`. The Accountable role can do the restricted creation, and the admin keeps the override. It is written only here, never also in §3, and the deployed rule carries its own `code` and `message` (e.g. "Only the hiring manager or an admin can create an offer").
  - **C = block:** a pre-transition `validation_rule` calling `{"has_consultation": ["<entity>", "<to_state>", {"var": "<id_column>"}]}`. Sequence it AFTER the notify transition (the consulted party must be notified before the gate can pass).
  - **C = read / R-ownership / owner-scoped rows:** the existing ownership `select_rule` (`$old.<owner> == $user_id`) read-scope; keep the advisory read grant.
  - **C = notify / I:** no rule — the `process_gates.emits_events` flag drives the platform's emit trigger → `raci_events`.
- **Behavior realization (living only):** when the entity has an approval gate, a restricted creation, a submit-then-lock rule, or owner-scoped rows (the analyst's Stage 5 / 7 / 10 decisions), realize them as live RACI checks instead of hand-authored rules: an approval → the A-gate above (in place of the `has_permission`-only gate rule) + at-most-one-A; a restricted creation → the create A-gate and its `create` `process_gates` row; submit-then-lock → R-ownership + a `submit_lock` `process_gate`; owner-scoped rows → the ownership `select_rule`. In `documentation` mode these stay hand-authored.

**Step 4 — Functional ownership.** Walk §9.2 rows. For each `responsibility | business function | default role | default tier`:
- The named default role gets the named default tier on this module's baseline. Mark `✨ functional ownership grant to be added` for the deployer's Stage 4l.
- Functional ownership maps the named `business function` (a real organizational unit) to a deployer-resolvable role at deploy time. The analyst doesn't auto-resolve here; the deployer's Stage 4l does the mapping (or surfaces a prompt if the function name doesn't match any live role).

**Step 5 — Boundary-crossing handoffs.** Per Writing Convention 10 on the architect, the blueprint's §6.2 / §6.3 handoffs for embedded_master entities whose catalog owner is absent are emitted under the installing unit. The analyst carries them verbatim, minus what "Dropped entities" removed, into the spec's §6 `### Outbound handoffs` / `### Inbound handoffs` sub-sections (nine blueprint columns, under both access scopes), with the source module set to the module where the entity lives (which may BE the installing unit). When the catalog owner installs, the deployer re-attributes the handoff to it.

The spec's §9 mirrors the blueprint's §9 verbatim (carry-forward), with three transforms: what depends only on a dropped entity is removed per "Dropped entities"; role slugs are normalized `-`→`_` per Step 1, because the blueprint's hyphenated `<system_slug>_<tier>` form is invalid as a `roles.slug`; and a persona override from the Additional Requirements is appended to that persona's `realization` per Step 3. The deployer creates the spec's normalized slug verbatim.
